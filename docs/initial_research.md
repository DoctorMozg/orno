# The crowded middle of declarative agent orchestration

**The core idea — a YAML/DSL-first multi-agent orchestrator with Jinja-templated prompts, targeted at CI/CD — is directionally correct but arrives in a category that crystallized during 2025 and is now being claimed by at least five serious incumbents.** Kestra just raised a $25M Series A (April 2026) around almost exactly this positioning, Microsoft Agent Framework 1.0 shipped April 3 2026 with YAML/JSON declarative agents and native GitHub Actions/Azure DevOps CI/CD support, GitHub itself launched Agentic Workflows (gh-aw) in February 2026 for markdown-to-GitHub-Actions compilation, Inngest AgentKit owns the TypeScript "deterministic routing" niche, and Temporal + OpenAI Agents SDK is becoming the default pattern for sophisticated teams (OpenAI Codex and Replit Agent both run on it). The structure-vs-freedom debate has effectively converged: the consensus answer in 2026 is **deterministic workflow layer + non-deterministic LLM activities**, which is exactly the design the user is proposing — but it is no longer a contrarian insight. Viability depends on finding a narrower wedge (multi-CI-portability, offline plan/preview, hard cost and eval gates) rather than claiming the overall category.

The critical observation: **the user's idea is effectively a Venn intersection of Kestra (YAML + templated prompts), GitHub Agentic Workflows (CI-native agent pipelines), Microsoft Agent Framework (declarative agents for DevOps), and Inngest AgentKit (deterministic orchestration with Jinja-like templating of system prompts from state).** Each of these competitors already ships the exact combination, with distribution or funding behind them.

## 2. Market signal assessment

**LLM agents in CI are moving from experimental to infrastructure, fast.** GitHub's own framing in the February 2026 launch post — "agents stop being a clever side project and start looking like infrastructure" — is the clearest market signal. Gartner projects 40% of enterprise applications will ship task-specific agents by end of 2026, up from <5% in 2025. A late-2025 Gartner survey found 40% of agentic AI projects will be cancelled by end-2027 due to reliability and cost overruns, which creates demand for "boring, reliable" platforms but has not translated into a single dominant winner.

**The pain with freeform frameworks is real and well-documented.** Production complaints about LangChain/LangGraph in 2025 cluster around four themes: latency overhead from abstractions (one engineer reported >1 second added per call), debugging opacity ("agents don't crash, they drift"), dependency bloat causing months-long unwinding, and silent failure modes. LangGraph 1.0's own release post openly acknowledged "the reliability gap hit hard … capable doesn't mean reliable at scale" — which is precisely the gap the user wants to attack, but LangGraph 1.0 is now *the* mainstream answer to that complaint, backed by Uber, LinkedIn, Replit, and Elastic case studies.

**The CI-specific vertical already has billion-dollar winners as closed products.** CodeRabbit (~2M repos, 13M PRs reviewed), Greptile ($25M Series A at $180M valuation, 82% bug-catch rate benchmark), Qodo ($40M Series A, Gartner Visionary), Bugbot (Cursor), and Macroscope have captured the high-value CI use cases — PR review, test generation, bug detection — as **products, not platforms**. They don't expose pipeline primitives, and most buyers aren't looking to assemble their own. The combined category raised >$1.2B in 2024–2025 per tracked data. This is both validation (demand is real) and threat (the highest-ROI use cases are already shrink-wrapped).

**For custom agent pipelines in CI, teams now have three emerging defaults.** First, GitHub Agentic Workflows for GitHub-native repos (shipped February 2026, Microsoft-backed, compiles markdown to hardened Actions YAML with sandboxing, network firewall, and safe-outputs). Second, Temporal + OpenAI Agents SDK for sophisticated backend teams who need durable execution — this is what OpenAI themselves use for Codex. Third, Kestra or n8n for teams that prefer declarative YAML and self-hosted — Kestra 1.0 explicitly positions as the "Declarative Agentic Orchestration Platform" and cites Apple, JPMorgan, Toyota, BHP as users.

**Funding confirms the category but not the specific DSL-first subgenre.** Kestra's $25M Series A in April 2026 is explicitly for "agentic orchestration." Inngest continues to raise on durable AI workflows. No 2025–2026 YC batch has produced a clear "deterministic agent CI" winner that isn't downstream of one of these platforms — suggesting the platform battle may already be played by well-capitalized incumbents.

## 3. Structure vs freedom: the debate is mostly settled

**The 2026 consensus is hybrid, and it is narrower than the user's framing.** Every serious production platform now separates a deterministic orchestration layer from non-deterministic LLM activities. Temporal's own blog post — "Of course you can build dynamic AI agents with Temporal" — explicitly articulates this: "Your Workflow is the orchestration layer… it needs to be deterministic. Your Activities are where the actual work happens: calling LLMs… These can be as unpredictable as needed." Dapr Agents ships the same split explicitly as two classes (DurableAgent for LLM-planned vs workflow-based for developer-defined). LangGraph's graphs are declarative skeletons with LLM nodes. Inngest AgentKit's "state-based deterministic routing" is the same idea in TypeScript. **The user's core thesis — structure the graph, let the LLM fill the slots — is correct, but it is now the mainstream, not a contrarian bet.**

**The bitter-lesson argument has lost the production discussion but kept the research one.** Practitioners in 2025–2026 uniformly cite reliability, observability, and cost as reasons to structure. Thought leaders including Hamel Husain, Shreya Shankar, and the DSPy and BAML authors have pushed "structure + evals" hard. Simon Willison's writing consistently emphasizes structured tools and observable pipelines over freeform agents. The pure-freedom camp survives mainly in agentic coding (Claude Code, Cursor, Devin) where the model itself is the runtime — and even those products are building increasingly structured subsystems for reliability (e.g., Claude Code's subagent/worktree patterns). The frontier of disagreement is no longer "should we use structure?" but "how much structure, and expressed in what language — code, graph, or DSL?"

**The DSL-vs-code sub-debate is where real differentiation lives, and DSL is losing at the high end.** Temporal, LangGraph, Inngest AgentKit, Dagster, and Prefect all chose code-as-workflow. The argument is that agent pipelines have too much conditional, stateful logic to express cleanly in YAML without re-inventing a programming language. Kestra and GitHub Agentic Workflows are the notable YAML/markdown bets; both are explicitly positioned for *less sophisticated* users (platform teams mixing languages, repo maintainers). This creates a classic fork: **DSL wins on accessibility and review-ability; code wins on expressiveness and ceiling.** A new entrant choosing DSL must accept competing with Kestra (massive plugin ecosystem, Pebble templates, Series A) for the accessible-users segment.

## 4. Template-engine-driven prompts: mostly solved

**Runtime Jinja/Handlebars-style prompt templating is table-stakes, not differentiation.** Kestra uses Pebble (Jinja-family) across all tasks including AI Agents, with access to inputs, outputs, and workflow state. Inngest AgentKit explicitly documents "dynamic system prompts" that pull from shared network State. GitHub Agentic Workflows' markdown *is* the prompt template, rendered with repository context at runtime. Langfuse, PromptLayer, Humanloop, and Braintrust all provide versioned prompt templates with Jinja-style substitution as managed services. Google's Dotprompt (.prompt files in Firebase Genkit) is purpose-built for this. Priompt (Cursor/Anysphere) pushes it further with JSX-like prompt composition.

**BAML and DSPy represent the structured alternative.** Rather than templating strings, they compile schemas and signatures into prompts, often with optimization (GEPA). Recent benchmarks show BAML wins on smaller models + nested output; DSPy wins with larger models and optimizer loops. The "DSPy/BAML vs Jinja templates" argument is live and unresolved — **but it is happening at the prompt layer, disconnected from workflow orchestration.** Combining a workflow DSL with Jinja prompts does not give you the optimization benefits of DSPy/BAML and does not meaningfully differentiate from Kestra's existing Pebble-in-tasks model.

**The only novel angle would be unifying workflow-graph-level template rendering with prompt optimization.** Something like: the DSL declares slots, the runtime can render them with Jinja for simple cases *or* drop in a compiled DSPy/BAML module for optimized cases, and optimization runs as a first-class CI step. No incumbent clearly does this end-to-end. But this is a subtle research-flavored wedge, not a product pitch.

## 5. The honest verdict: viable but derivative, needs a sharper wedge

**The idea is not bad, but as described it is directionally late and tonally generic.** Every core ingredient — deterministic orchestration, DSL config, Jinja prompts, CI/CD focus, OSS-core-plus-SaaS — maps to a funded or about-to-ship incumbent. The strongest honest critique is that the user is proposing to rebuild the intersection of Kestra and GitHub Agentic Workflows at a time when Kestra just raised $25M and GitHub is bundling the same category for free into every repo on Earth. Against that, "OSS framework for DSL-defined agent pipelines" is not a winning pitch.

**However, three real gaps exist that nobody owns cleanly.**

First, **multi-CI portability.** GitHub Agentic Workflows is GitHub-only by design; Microsoft Agent Framework's CI story is GitHub Actions + Azure DevOps; Kestra is its own runtime, not a CI-native artifact. There is no well-adopted declarative agent-pipeline spec that runs identically on GitLab CI, Jenkins, CircleCI, Buildkite, and GitHub Actions. A portable YAML spec that compiles to each platform's native YAML (similar to how Dagger tried this for builds, or Earthly for Docker) could carve out a real niche — especially for enterprises on GitLab Ultimate or self-hosted stacks where gh-aw does not reach.

Second, **offline `plan`/`preview` semantics.** Terraform won because `terraform plan` gave engineers confidence before apply. No current agent platform offers a credible "what would this agent pipeline do, approximately, for these inputs, without calling the LLM" mode — or a simulated dry-run with recorded responses. For CI specifically, where cost and blast radius matter, this would resonate with SRE buyers.

Third, **cost, eval, and policy gates as first-class primitives.** Kestra and Temporal treat cost as an afterthought; gh-aw has sandbox and safe-outputs but no native budget gates; LangGraph/Inngest have observability but not policy. A platform where every agent pipeline ships with token budgets, eval gates (minimum DSPy/BAML score to proceed), and declarative approval policies baked into the DSL — enforced by the runtime, not as after-the-fact dashboards — would actually differentiate. This is the "SOC2 for agents" angle, and it aligns with EU AI Act trajectories toward mandatory auditability.

**If the user ships this, the sharpest positioning is not "Terraform for agents" or "Dagster for agents" — both are claimed or strained.** The strongest framing is **"Portable agent pipelines for your existing CI, with budgets and evals as first-class gates."** A one-liner along the lines of *"Write your agent pipeline once in X-DSL, compile it to GitHub Actions / GitLab CI / Jenkins, ship it with budgets and evals as gates, audit every run by default."* That positions against gh-aw (not portable), against Kestra (separate runtime), against Temporal (too heavy for CI), and against DIY (no eval/budget gates).

## 6. Key risks and counterarguments

**"Temporal already does this."** For sophisticated teams, yes. The counter is that Temporal is a separate runtime requiring workers, Cassandra/Postgres, and an ops investment most CI workloads do not justify. The wedge is the cohort between "I'll just use GitHub Actions" and "I'll stand up Temporal" — teams that need more than Actions gives natively but do not want to operate Temporal. That cohort exists but is narrower than a VC-scale market.

**"LangGraph 1.0 is structured enough."** For in-process agent apps, largely yes, and the user is well aware of this. LangGraph is an SDK not a pipeline format, though. The counter holds that LangGraph nodes are Python code, not a reviewable DSL, and do not integrate natively with CI YAML. A `langgraph.yaml` equivalent is missing, but LangChain could ship one quickly if the niche proves real.

**"Teams just use GitHub Actions with Claude/Copilot CLI."** This is the most dangerous counter. gh-aw plus Copilot/Claude/Codex CLIs covers 70–80% of the practical CI use cases for repo automation with zero new infrastructure. For anyone already on GitHub, any new framework has to beat "markdown file in `.github/workflows/`" — a very high bar.

**"Kestra already claims this."** Kestra's positioning — YAML-declarative, agentic orchestration, Pebble (Jinja) templating, CI/CD friendly, 1200+ plugins, $25M Series A, declared customers including JPMorgan and Apple — is uncomfortably close to the user's description. The honest reading is that Kestra has probably won the generalized declarative-agent-orchestration category for the next 18–24 months unless something dramatically differentiated appears. A new project must either target a use case Kestra neglects (CI-native, not a separate runtime) or an ecosystem Kestra underserves (the TypeScript/Node world dominated by Inngest rather than by a YAML runtime).

**"Microsoft Agent Framework will suffocate the category."** With 1.0 GA on April 3, 2026, multi-language support, declarative YAML/JSON, native Azure DevOps/GitHub Actions integration, OpenTelemetry, and Entra ID — this is the enterprise default path for any Microsoft-adjacent shop. It is not a threat to scrappy non-enterprise users, but it puts a ceiling on enterprise ACVs.

**"AI-native CI/CD" as a positioning line has been grazed but not yet definitively claimed.** Nobody owns the phrase clearly. GitHub's "Continuous AI" framing is closest and is a soft claim. A well-executed OSS project could own this phrase, but it is a marketing lane, not a defensible moat.

## Bottom-line verdict for career and commercial viability

**As a career-positioning open-source project: strongly worth doing**, especially if scoped as the portable-multi-CI + budgets/evals-as-gates angle. The space is hot, the user's technical framing is correct, and shipping something opinionated here will read as credible to every GenAI infra team hiring in 2026. Do not try to out-Kestra Kestra or out-gh-aw GitHub.

**As a commercial venture: high risk, tight window.** The OSS-core-plus-SaaS model has two funded incumbents (Kestra, Inngest) in adjacent spaces, plus Temporal, plus Microsoft, plus GitHub itself giving away the CI-native version for free. A pure commercial bet likely needs to (a) attach to a specific pain Kestra/Inngest/Temporal underserve — multi-CI portability and policy gates are the best candidates — and (b) have a credible plan to ride the EU AI Act / SOC2 compliance wave, where "deterministic, audited agent pipelines" becomes a regulatory requirement rather than a preference. Without one of those, it is a feature, not a company.

**Don't position it as "the opposite of Claude Code."** Claude Code is winning its category. The right framing is orthogonal: *"Claude Code is for humans driving agents interactively. This is for agents running on a schedule or trigger — the same pipeline every time, with budgets, evals, and audit logs by default."* That is defensible, technically precise, and does not force a false choice.
